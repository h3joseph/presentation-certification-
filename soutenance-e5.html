Pourquoi ces deux outils
Déjà mis en place à l’Épreuve 3 pour surveiller le modèle IA, Prometheus et Grafana sont ici étendus à l’ensemble de l’application : Prometheus détecte et quantifie, Grafana rend l’ensemble consultable en un coup d’œil. Les deux sont opérationnels en environnement local, aux côtés de l’API et du dashboard.

Seuils

Des seuils chiffrés, pas des impressions

Fraîcheur des données terrain
< 7hseuil d’alerte
Collecte prévue toutes les 6h, +1h de marge avant de considérer que les données ne remontent plus
Erreur du modèle de correction
< 3°Cseuil d’alerte
Au-delà, la prévision devient trop imprécise pour aider une décision sur le terrain
Taux d’erreur de l’API
< 5%requêtes / 5 min
Une erreur isolée reste possible ; une panne qui touche beaucoup d’appels est signalée
Temps de réponse de l’API
< 1spour 95% des requêtes
L’interface reste fluide, même si plusieurs personnes la consultent en même temps

La santé des conteneurs complète ces seuils par un statut opérationnel, sans valeur chiffrée

Portée du dispositif

Ce que la surveillance détecte, et ce qu’elle ne détecte pas encore

Défaillance bruyante
Une erreur qui interrompt un traitement et remonte dans les journaux
Absence de résultat
Un panneau ou une métrique qui reste vide alors qu’une donnée est attendue
Erreur silencieuse
Un code qui s’exécute sans planter mais produit un résultat faux, non détecté aujourd’hui

Ce dispositif n’a pas empêché les incidents. Il a changé la façon dont ils ont été trouvés. Trois incidents réels le montrent.

Trois incidents techniques réels

Incident 1

L’API ne répond plus

Statut global API
Rouge
Le service ne répond plus
Taux d’erreur HTTP 5xx
100%
Toutes les requêtes échouent

Constaté directement sur le tableau de bord de supervision

Incident 1

Diagnostic et correction

  1. Symptôme
    Panneau rouge, 100% d’erreurs 5xx
    Toutes les requêtes envoyées au serveur échouent
  2. Pistes
    Conteneur arrêté, base injoignable, ou table absente
    Trois hypothèses envisagées avant de trancher
  3. Cause
    La base n’avait pas encore été initialisée
    Conteneur actif, connexion à la base correcte, mais une table attendue n’existe pas encore dans la base de données
  4. Correction
    Script d’initialisation exécuté, puis automatisé
    Exécution manuelle immédiate du script de création des tables, puis intégration au démarrage de l’API
  5. Prévention
    Initialisation automatique à chaque lancement
    Les indicateurs repassent au vert ; l’incident ne peut plus se reproduire silencieusement au démarrage

Consigné dans docs/incident_log.md (Incident 9) — le même outil de suivi utilisé pour tous les incidents du projet, versionné sur github.com/h3joseph/certification-

Incident 2

Le tableau de bord n’arrive pas à contacter l’API

Requêtes API par endpoint
0
Sur deux routes normalement interrogées
Message utilisateur
Erreur
« API inaccessible » sur les pages concernées

Constaté sur le tableau de bord de supervision et signalé par les utilisateurs

Incident 2

Diagnostic et correction

  1. Symptôme
    Compteur à zéro sur deux routes
    Les utilisateurs obtiennent un message indiquant que l’API est inaccessible
  2. Pistes
    Origine API ou origine dashboard
    Requêtes envoyées directement vers les deux routes : réponses valides, l’API fonctionne normalement
  3. Cause
    Adresse de secours mal orientée
    L’adresse de l’API n’est pas définie dans la configuration ; l’adresse de secours utilisée pointe vers le tableau de bord lui-même
  4. Correction
    Adresse correcte ajoutée à la configuration
    Fichier de configuration du tableau de bord corrigé, application redémarrée
  5. Prévention
    Communication revérifiée après correction
    Une nouvelle série de requêtes confirme le rétablissement de la communication et de l’affichage des données

Consigné dans docs/incident_log.md (Incident 10) — le même outil de suivi utilisé pour tous les incidents du projet, versionné sur github.com/h3joseph/certification-

Incident 3

Un test automatique échoue en intégration continue

INFOGitHub Actions : exécution de la suite de tests
ERRORUn test échoue : réponse de succès attendue, réponse d’erreur renvoyée

Constaté après un envoi de code, dans la chaîne d’intégration continue

Incident 3

Diagnostic et correction

  1. Symptôme
    Un test échoue à l’envoi de code
    Réponse de succès attendue, réponse d’erreur renvoyée par l’API testée
  2. Pistes
    Panne réseau, dysfonctionnement de l’API, ou test mal écrit
    Les autres tests réussissent tous : problème réseau et dysfonctionnement général de l’API écartés
  3. Cause
    Préfixe manquant dans l’URL utilisée par le test
    Comparaison de l’adresse testée aux routes réellement exposées par l’API
  4. Correction
    Préfixe ajouté à l’adresse utilisée dans le test
    Chaîne d’intégration continue relancée
  5. Prévention
    Ensemble des tests validé avec succès
    Confirmation que le problème provenait uniquement du test, non de l’application

Consigné dans docs/incident_log.md (Incident 11) — le même outil de suivi utilisé pour tous les incidents du projet, versionné sur github.com/h3joseph/certification-

Bilan

La surveillance n’a pas empêché les incidents, elle a changé comment ils ont été trouvés

Incidents 1, 2 et 3
Chacun rendu visible par un signal net : panneau rouge, compteur à zéro, test qui échoue — jamais une relecture de code à l’aveugle
Limite assumée du dispositif
Un calcul figé ou une insertion jamais réalisée resteraient aujourd’hui invisibles : la cohérence logique d’un résultat dans le temps n’est pas encore couverte
Chaque résolution a renforcé le dispositif
Une correction de code vérifiée par un test, et à chaque fois une métrique, un test, ou une documentation en plus pour reconnaître immédiatement un problème similaire
