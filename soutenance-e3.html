Pourquoi GitHub Actions

GitHub Actions
Le code est déjà hébergé sur GitHub : déclenchement automatique, aucune configuration réseau ni serveur dédié à maintenir
Jenkins / GitLab CI
Écartés : infrastructure supplémentaire à installer et maintenir, disproportionnée pour ce projet
Un fichier, des étapes reproductibles

CI/CD · Fonctionnement

Deux déclencheurs, un principe : fail-fast

Push sur main
Toute modification envoyée sur la branche principale déclenche la chaîne
Pull request
Relecture avant acceptation, pour constater les erreurs le plus tôt possible
Fail-fast
Chaque étape doit réussir avant que la suivante commence. Si une étape échoue, l’exécution s’arrête immédiatement : on n’avance jamais un build ou un déploiement alors qu’un problème est déjà détecté

CI/CD · Étape 3, en détail

Le modèle ne peut pas être réentraîné à chaque changement

Les données d’entraînement sont volumineuses et volontairement absentes du dépôt Git. Réentraîner un modèle complet à chaque modification, même sans lien avec l’IA, serait inutilement coûteux.

Contrôle 1 · Jeu d’exemple
Entraînement complet sur un petit jeu de données rangé avec le code : validation, préparation, découpage temporel, entraînement des candidats, comparaison, contrôle de sécurité. Vérifie que le cycle fonctionne toujours
Contrôle 2 · Modèle réel
Le modèle réellement utilisé, entraîné à part sur l’ensemble des données, doit continuer d’améliorer les prévisions brutes d’Open-Meteo
Deux contrôles complémentaires
Le premier garantit que le cycle d’entraînement reste fonctionnel, le second que le modèle en service reste performant. Si l’un des deux échoue, la chaîne s’arrête : rien n’est déployé

Encore faut-il garantir, à chaque changement, que le code fait bien ce qu’il est censé faire.

Programmer les tests automatisés du modèle

Tests automatisés

La pyramide des tests

Stratégie popularisée par Mike Cohn : beaucoup de tests rapides à la base, de moins en moins mais de plus en plus complets en montant. Un seul type de test ne peut pas tout couvrir.

Pourquoi cette répartition
Un test unitaire rapide ne détecte pas un problème d’intégration entre deux composants ; un test de bout en bout, plus complet, est trop lent pour être exécuté à chaque modification mineure

Tests automatisés

Six niveaux, du plus rapide au plus complet

Bout en bout Seule à utiliser une vraie base PostgreSQL complète, conditions proches du réel
Performance Temps de réponse maintenus même avec un volume de données plus important
Contrat Forme des réponses de l’API stable : noms de champs, types, codes d’erreur
Intégration Plusieurs parties du projet ensemble, avec une vraie petite base de test
Qualité des données Bonnes colonnes, valeurs dans les bonnes bornes, pas de doublons
Unitaires Une seule fonction à la fois, par centaines, en quelques secondes

Tests automatisés

Les bibliothèques utilisées

Pytest
Moteur principal, exécute les tests et permet de les étiqueter selon leur niveau
Pytest-cov
Calcule automatiquement la proportion du code exécutée par au moins un test
Httpx
Envoie de fausses requêtes vers l’API directement en mémoire, sans serveur lancé
unittest.mock
Remplace un vrai appel (Internet, base de données) par une version simulée

Développer une API exposant le modèle IA

API · Modèles exposés

Deux modèles, une seule API REST

AIFS · Open-Meteo
Développé par le Centre européen pour les prévisions météorologiques à moyen terme (ECMWF), explicitement référencé par un paramètre dédié, contrairement à WeatherAPI, qui ne documente pas son modèle interne
Correcteur de biais
Entraîné avec scikit-learn, il apprend à corriger l’écart entre la prévision Open-Meteo/AIFS et la température réellement mesurée sur le terrain

Les deux modèles sont mis à disposition de manière uniforme via l’API REST déjà créée pour le projet

API · Entraînement

Entraîner le correcteur de biais

Récupération depuis la BDD→ Découpage temporel→ Candidats entraînés→ Comparaison MAE
Jamais de découpage aléatoire
Le découpage temporel évite qu’une heure du jeu de test soit trop proche dans le temps d’une heure du jeu d’entraînement pour la même station, ce qui fausserait l’évaluation
Garde-fou de sécurité
Le meilleur candidat n’est conservé et exporté que s’il améliore réellement la prévision brute. Sinon, aucun modèle n’est mis à disposition

API · Choix d’architecture

Le modèle vit exclusivement dans l’API

Dashboard allégé
Charger un modèle scikit-learn exige scikit-learn et Joblib. En centralisant dans l’API, le dashboard n’a besoin que des bibliothèques d’affichage
Une seule copie
Évite de charger plusieurs copies du même modèle à différents endroits : performances et incohérences lors des mises à jour
Accessible partout
Exposer le modèle via une API REST le rend accessible depuis n’importe quelle technologie capable d’une requête HTTP

Sauvegardé via Joblib, rechargé une seule fois au démarrage grâce à un mécanisme de cache. Fichier absent ou indisponible : message d’erreur explicite, jamais un échec silencieux

API · Points d’accès

Deux points d’accès dédiés au modèle

Prévisions corrigées
Nom de station en paramètre, horizon en jours optionnel. Réponse heure par heure : prévision brute et corrigée. Code d’erreur adapté si la station ou le modèle sont indisponibles
Informations sur le modèle
Algorithme retenu, performances sur le jeu de test, résultats de la prévision brute, pourcentage d’amélioration, période de données d’entraînement

Dashboard · Intégration

Pourquoi Dash, et pourquoi un service séparé

Dash
Met à jour l’affichage sans recharger toute la page, reste entièrement en Python, fonctionne très bien avec Plotly déjà utilisé ailleurs dans le projet
Streamlit / app JS séparée
Écartés : second langage ou moins bien intégré au reste du projet Python
Un service, pas une bibliothèque chargée
Le dashboard tourne dans son propre service, séparé de l’API. Même image de base, dépendances différentes : le dashboard n’installe que les bibliothèques d’affichage, sans les bibliothèques d’apprentissage automatique

En développement, le dossier du projet est monté dans le conteneur : effet immédiat des modifications, sans reconstruction · code versionné sur github.com/h3joseph/certification-

Monitorer le modèle en continu

Monitoring · Modèle IA

Une surveillance classique ne suffit pas

Le climat évolue d’une saison à l’autre, un capteur terrain peut dériver, la correction de biais peut devenir moins précise sans aucune erreur technique visible. La surveillance classique (disponibilité, erreurs, temps de réponse) ne dit rien de la pertinence du résultat produit par le modèle.

Prometheus
Récupère régulièrement des métriques exposées par les différents services du projet
Grafana
Transforme ces métriques en graphiques compréhensibles pour suivre l’évolution du système
6Cibles surveillées
15 sIntervalle d’interrogation

API, dashboard, PostgreSQL, Prometheus lui-même, ressources système, conteneurs Docker

Monitoring · Métriques

Deux métriques que rien ne fournit automatiquement

Erreur moyenne du modèle
À chaque interrogation, un programme récupère les derniers résultats de la table des scores du benchmark ; les tables stations et sources apportent des noms lisibles plutôt que de simples identifiants
Fraîcheur des données terrain
Dernière remontée reçue par station, puis nombre d’heures écoulées depuis. Un modèle ne peut pas être évalué correctement si les données terrain ne sont plus mises à jour

Recalculées à chaque interrogation, jamais mises en cache. Collecteurs chargés automatiquement dès le démarrage de l’API · code des collecteurs versionné sur github.com/h3joseph/certification-

Monitoring · Rigueur

Vérifier avant de considérer une métrique opérationnelle

  1. aCollecteur modifié, rechargement auto en développement
  2. bEndpoint métriques de l’API : la métrique est bien exposée
  3. cInterface de requête Prometheus : la métrique est bien récupérée
Le développement comme bac à sable
Exposer une métrique ne garantit pas qu’elle soit réellement collectée. Sans l’étape (c), un décalage entre la configuration de Prometheus et le code applicatif ne serait jamais détecté avant la mise en service
